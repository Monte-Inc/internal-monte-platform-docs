Monte fails closed. When it declines, it exits 3 or higher and prints `CODE: cause (fix)` on stderr. Read the fix first: it is usually the answer. The [exit-code table](/cli/overview#exit-codes) lists every code.

## Common refusals

### train refuses with E_NO_BASELINE

The Cohort has no Baseline eval. Run `monte eval <measurement>` first, which scores the `dev` Split and records `eval@0`. That dev Baseline is the only one training checks for, and every Cohort needs its own.

Take the `test` read as well, with `monte eval <measurement> --split test`, before you train anything. Training does not require it, so nothing refuses if you skip it. The final claim does require it, and it can only be taken before the first training Run. The next entry is what happens when you skip it.

### A test eval refuses: this Cohort has no test baseline

You trained before scoring the base model on `test`, so there is nothing for the final claim to be compared against. The cause reads:

```
E_PREFLIGHT: this cohort has no test baseline (test@0), so a checkpoint test eval would spend the final touch with nothing to pair against — the test delta would be forfeit forever
```

Monte reads `test` exactly twice in a Cohort. The first read is one you run yourself, on the base model, with `monte eval <measurement> --split test` before any training. The second read is the final claim. `monte eval` scores `dev` unless you pass `--split test`, so the Baseline eval alone never touches `test`.

There is no way to fix this inside the Cohort you are in. Once a Checkpoint exists, the first read can no longer be taken, and no honest test delta can be produced there. Start a fresh Cohort and take both Baselines before you train. In practice that means a new experiment with `monte experiment init`, because a Cohort is a group of Runs inside one Measurement's Ledger.

### The final claim refuses to select a Checkpoint

You do not pick the Checkpoint the final claim scores. Monte does: it takes the Checkpoint whose `dev` score improved most over the Baseline, compared task by task.

That comparison needs the per-task results file for the Baseline and for every Checkpoint scored on `dev`, not just the leading one. If one of those files cannot be read, Monte refuses to select at all with `E_PREFLIGHT` rather than choosing among the rest, because the true winner could be exactly the Checkpoint it cannot read.

Run `monte eval <measurement> --split test` where the run directories live, which is the box.

### E_CONFIRM in a script

Two causes, one code. For `eval` and `train` without a TTY: pass `--yes`. For `promote`: pass `--confirm <measurement-name>`, typed exactly.

### A lock refuses my command

One lock per Measurement. If the holding process is alive, wait for it or `monte stop` it. If it died on this host, the next command reclaims the lock automatically. If the machine that held the lock is gone, remove the `.lock` file by hand. It sits in the Measurement's directory under your data root, which `monte config` prints as `data_root`.

### My Run mocked, or refused to mock

Whether a Run is real or mock is decided by what is installed on the box. A Run is real when the stack it needs is present: the serving stack for an eval, the pinned training container for a train. On a GPU machine missing the stack a Run needs, Monte refuses that Run and prints the reason. It never quietly records a mock row in place of the real one you asked for.

"The stack" is the NeMo Gym checkout and the vLLM serving venv under `MONTE_LOCAL`, which defaults to `~/monte`. A box launched with `monte box up` installs the stack itself the first time you submit a `--remote` job to it, so this refusal means you are on a GPU machine that was set up some other way. If the stack is installed elsewhere, point `MONTE_LOCAL` at it.

A mock-only Environment declares no Gym benchmarks, so it has nothing to run for real and mocks freely anywhere. Once a Measurement holds real evidence, Monte refuses mock Runs into it.

### env install refuses: data does not match the manifest

Every frozen file is hashed on every read and compared against the hash `manifest.json` pins. The refusal names the file and both hashes, and which fix applies depends on which copy is wrong.

- **The copy inside the Gym checkout**, the one Gym reads, is missing, stale, or was edited in place. This one usually surfaces at preflight rather than at install. Re-run `monte env install <name>` to write it again from the frozen files.
- **The frozen file on the data root is missing** or unreadable here. Check `monte env list --vault` first. The repair is a refetch, so it needs the Vault to hold this Environment.
  - **It is in the Vault.** Move the Environment's directory out of the data root rather than deleting it, somewhere `monte env list` does not look, then run `monte env install <name>`. Getting it out of the way is the load-bearing half, because install decides by the manifest: a directory that still holds one gets verified, not refetched. With it gone, install pulls the whole thing and proves every hash. Delete what you moved once that succeeds, and not before: a pull can fail its own hash check, and then the copy you set aside is the only one left. Install registers into the NeMo Gym checkout, so run it on a machine whose `MONTE_LOCAL` holds the stack.
  - **It is not.** A package you author never enters the Vault, and neither does an add that ran without a key that can write it. Delete nothing: the data root holds the only copy there is. Once bytes are gone they are gone, and the manifest still claims the name, so freezing it again under that name refuses. For a local-only freeze, add it under a new name with the same `monte env add` form that froze it. For a package you author, `monte env add` never ran, so the answer is the copy [the authoring page](/environments/authoring) tells you to keep.
- **The frozen file on the data root drifted** since it was pinned. Same repair, same precondition, and the same guard: check `monte env list --vault` first. If it is there, move the directory out of the data root, install again, and the pinned copy comes back. Delete what you moved once the install succeeds. If it is not, delete nothing. The drifted directory is the only copy of those bytes, and the pinned ones are gone. There is no repair for the edit itself, either way. Rows that changed after they were pinned are a different Measurement, and they can enter Monte again only under a new name.

Never regenerate frozen Splits on a box to repair them. A regenerated copy will not hash to what the manifest pins, so it refuses the same way.

### E_REMOTE: the tree is dirty or unpushed

`--remote` runs the commit origin holds, so the box can re-derive the Run. Commit and push, then submit again. The same code covers a box that cannot serve the Run, such as one launched with `--cold`. A cold box has no data root. It has nowhere to read the Measurement from or write the Run's rows to, so it cannot serve a real Run. The Vault holds frozen Environments and Datasets, not a Measurement's own files.

### E_BOX or E_STORAGE: no credentials

Both name the variable they wanted. `box` and `--remote` need a Lambda key. `sync`, `push`, `env list --vault`, and `dataset list --vault` need a GCS key and refuse without one. A real remote train needs a Hugging Face token. The [environment-variable tables](/cli/overview#environment-variables) list each one and its 1Password fallback.

The two ladders are not symmetric. A read resolves `MONTE_GCS_KEY_FILE`, then `MONTE_GCS_KEY_OP`, and stops. A write tries `MONTE_GCS_BOX_KEY_FILE`, then `MONTE_GCS_BOX_KEY_OP`, then falls back to that read pair, which on a laptop holds a key that cannot write. So the box key alone leaves every read with no credentials at all. The ordinary key alone is worse to diagnose: a write resolves it, and then fails on the bucket rather than on the lookup. `monte push` returns `E_STORAGE` for a key that is set, and a Vault freeze quietly stays local.

A fetch with no read key refuses as `E_NOT_FOUND` rather than as a credentials problem. That covers `monte env install` on a name this data root has never held, and `monte dataset show` on a Dataset it does not hold.

### My freeze did not reach the Vault

`env add` and `dataset add` never refuse for a GCS key. They do refuse for a Hugging Face token, which `--server` and `--from-hf` need. Writing the Vault needs the read-write key, and a laptop's ordinary key is read-only there, so a laptop needs `MONTE_GCS_BOX_KEY_FILE` or `MONTE_GCS_BOX_KEY_OP` set. Without one the freeze still happens, on this data root alone, and the note says so and names the key.

Freeze again as soon as you have the key. Move the local copy out of the data root first, because the name is claimed there and an add refuses a name it already holds. Nothing is bound to a new Environment yet, so a re-freeze costs nothing today. Once a Baseline exists, a re-freeze is a different Measurement and the moment has passed.

A freeze with no key for the Vault also checks this data root alone for the name, so a name another region already claimed is not refused here until a freeze can reach the Vault.

### An add failed after it froze

Losing the name to another region is the case that changes your data root. Monte removes the manifest it just wrote, because a local manifest under a name another region's bytes now own would be a lie no later command could correct. The frozen files stay on disk, and nothing discovers them.

Every other push failure keeps the freeze. A dropped connection, an IAM change mid-flight, a Ctrl-C during a multi-gigabyte upload: none of them took a name from anyone, and prepare can be expensive to run again, so the Environment is left exactly where a keyless freeze would leave it. The command refuses with `E_STORAGE` rather than exiting clean, and the refusal says the freeze survived and names the directory holding it. Treat what you have as the entry above.

The lost-race refusal names both halves of its fix. Re-add under a new name, which is `--as` for an Environment and the name argument for a Dataset. Then bring the winner's copy here: `monte env install <name>` for an Environment, `monte dataset show <name>` for a Dataset.

### Training preflight refuses: disk

The refusal names the free-space minimum and which filesystem is short, home or the data root. Free disk there and run again.

## A stuck run

`monte logs <measurement>/<run> --follow` tails the event file. `monte stop <measurement>/<run>` terminates it: the row reads as abandoned, and the Ledger keeps it.
