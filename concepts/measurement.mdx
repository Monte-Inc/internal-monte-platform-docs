---
title: "Measurement"
---

A Measurement is a fixed standard for scoring a model. Two Runs under the same Measurement answered the same tasks under the same rules, so you can compare them directly.

A Measurement is built on one [Environment](/concepts/environments). It fixes which of that Environment's tasks run, the sampling rules, and what counts as correct.

## Why a Measurement exists

Evaluation has many variables. You can give each task one attempt or several. You can change the decoding temperature, the subset of tasks that runs, or how strictly the grader marks an answer.

Each of those returns a different number for the same model. None of them is wrong. They answer different questions about how well the model does the task.

A Measurement holds those variables constant. Within one Measurement, the model is the only thing that changed between two Runs. You can define as many Measurements as you want.

When the variables go unrecorded, old results stop being usable. You cannot tell why two numbers differ, so you cannot compare the experiments that produced them.

## What a Measurement fixes

A Measurement fixes three things when you create it.

1. **The tasks.** Which tasks run, as an exact list. Not a count and not a name, but those specific tasks.
2. **The eval settings.** How the model is sampled: the decoding, the temperature, and how many attempts each task gets.
3. **The grading.** Which grader scores the answers, and the prompt the model saw.

A Measurement fixes the evaluation only. It does not fix the training method. The [Recipe](/concepts/runs-ledger#recipes), the hyperparameters, and the training data all stay free, because those are what the agent changes between Runs.

A Measurement names no model either. Each Run binds its own, so many models can compete under one Measurement.

Monte checks the frozen material before every Run. If any of it changed, that is a different Measurement, and Monte refuses to score the new Run against the old ones.

## The Splits

A Measurement owns its three Splits. The trainer and the evaluator both read the same lists, which is what holds the roles below in place.

- **`train`.** What the model learns on.
- **`dev`.** What the agent reads to choose its next move.
- **`test`.** Held back for the Baseline and the final claim.

The agent picks each next move from what `dev` shows, so the loop fits itself to those tasks over time. A `dev` score overstates the model, and `dev` is not the number you report. `test` stays out of the loop. Monte reads it twice, once at the Baseline and once for the final claim, and refuses a third. [The loop](/concepts/loop) covers how those reads happen.
