An Environment is the world an agent acts on. The agent takes an action, the Environment returns a new state and a reward, and the cycle repeats. The reward is the proxy for the behavior you want.

Monte builds on [NeMo Gym](https://docs.nvidia.com/nemo/gym/) and adds two things that make agent-assisted training possible:

- **Split roles.** The improvement loop optimizes against `dev`, so `dev` cannot be the number you report, and `test` is held back for that.
- **A fingerprint.** The tasks, the grader, and the harness configuration each change a score without looking like a change to the measurement. The fingerprint hashes the Environment's frozen material, for a trainable Environment its training data included, and refuses a Run when any of it changes.

## Parts of an Environment

An Environment has three parts, and the agent harness sits beside them.

**Task material.** The tasks, plus the data needed to score each attempt. One task is one problem for the model: a coding issue to fix, a tool-calling scenario to work through, a support conversation to resolve. The prompt config that renders a task into a model call belongs here too.

**Grader.** It scores one attempt into a reward, usually between 0 and 1, by checking the output against the task's own data: an expected answer, a test suite, or a rubric. It defines what "good" means for this Environment, and it serves two jobs at once, because its scores become both the eval metric and the training reward.

**Tools and state.** The per-task world that the agent changes as it acts. Each attempt starts from a clean state, so a reward belongs to that attempt alone. State ranges from none at all to a file system, a database, or a repository that the agent edits. Environments are single-turn today: one question in, one answer out, no tools and no state.

**Agent harness.** The harness works with an Environment, but the Environment does not own it. A model on its own does stateless inference, and the harness is what makes it an agent: it loops model calls, routes tool use, manages context, and decides when a task is done. A simple harness only loops until the task completes, while others add planning, memory, and skills. Each Run states which model it uses.

Every Environment must have a grader. Ungraded rows enter Monte only one way: frozen as a Dataset and stated as an sft Run's Source, never as part of an Environment or a Measurement. One Environment can serve several Measurements: the same tasks, frozen under different settings.

You can measure any environment from the NeMo Gym catalog, or write your own as an installable package.

## Where an Environment lives

A frozen Environment lives in the Vault, a cloud bucket that outlives any box. That is the copy Monte treats as true.

The copy on your data root is a materialization of it. `monte env add` freezes the files, hashes them, and pushes them to the Vault. `monte env install <name>` fetches them back and proves every hash before it writes them. So you can delete the local copy and get it back, and losing a box, or the disk its data root sits on, costs you no Environment that reached the Vault. Both halves need cloud credentials, the push and the fetch alike.

Two kinds never reach it. An add that runs with no credentials freezes on the data root alone and says so. An Environment you ship as a package is never pushed at all. Those two you hold yourself. An add whose key resolves and then cannot write is a third case, and a safer one: it refuses and takes its own manifest with it, so nothing is left claiming the name.

`monte env list --vault` answers the only question that matters before you delete a local copy: whether the Vault holds this Environment. It reads the network, so a machine with no credentials cannot ask.

Freezing is the only step that writes to the Vault. After that the flow runs one way, Vault to data root to Gym checkout, and no copy can change the one above it. A frozen Dataset lives there under the same rules, and `monte dataset show` is what fetches one back.

The reason to keep the bytes is the fingerprint. Freezing the same tasks a second time runs Gym's prepare again, and prepare reads live sources, so the files come back different. Different files are a different fingerprint, and a different fingerprint is a different Measurement. Every Baseline taken under the old one is then worth nothing. The bytes have to survive, because they cannot be made twice.

That is the rule behind all of it: a data root is where things are materialized, not where they live. Frozen inputs belong to the Vault, Checkpoints to Hugging Face, and a Run's Traces, results, and events to the results bucket. What breaks the rule you own yourself: the two kinds above, and a Run's evidence before `monte push` sends it. Push is a deliberate act, and until it runs the data root holds the only copy of that Run.

## How a graded rollout runs

A rollout runs across three servers: one for the model, one for the agent harness, and one for the Environment's grader.

1. The harness reads one Task from the Split. The Split is a list of task IDs.
2. The harness sends the Task to the model server, with the prompt already applied, and collects the reply.
3. The harness sends the reply to the grader.
4. The grader returns a reward and the answer that it extracted.
5. Monte records one Trace for each Task, then writes the score to the Ledger.

A training Run uses the same grader, and although eval and training each run their own copy of it, preflight proves that the copies match. The reward that the model learns from and the score that the eval reports therefore come out of one implementation.
