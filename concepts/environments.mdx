title: "Environments"
---

An environment is the world an agent acts on. The agent takes an action, the environment returns a new state and a reward, and the cycle repeats. The reward is the proxy for the desired behavior.

Monte builds on [NeMo Gym](https://docs.nvidia.com/nemo/gym/) and adds two structures that make agent-assisted training more reliable:

- **Splits:** The improvement loop optimizes against the dev split, so dev cannot be the reported result, and the test split is held back to produce it.
- **Fingerprint:** The fingerprint hashes the environment's frozen material and refuses a run when any of it changes. Without it, the tasks, the grader, or the harness configuration could change silently and lead to different results.

## Parts of an Environment

An environment has three parts, and the agent harness sits beside them.

**Tasks:** The tasks, plus the data needed to score each attempt. One task is one problem for the model: a coding issue to fix, a tool-calling scenario to work through, a support conversation to resolve. The prompt config that renders a task into a model call belongs here as well.

**Grader:** It scores one attempt into a reward, usually between 0 and 1, by checking the output against the task's own data: an expected answer, a test suite, or a rubric. It defines what success looks like for this environment, and it can serve two roles: its score can be the eval metric, or it can serve as the training reward.

**Tools and State:** The per-task world the agent acts on. Tools are the actions available to it, and state is what those actions change. Each attempt starts from a clean state, so a reward belongs to that attempt alone. State ranges from none at all to a file system, a database, or a repository that the agent edits. Environments are single-turn today: one question in, one answer out, no tools and no state.

**Agent Harness:** A model on its own does stateless inference, and the harness is what makes it an agent: it loops model calls, routes tool use, manages context, and decides when a task is done. A simple harness only loops until the task completes, while others add planning, memory, and skills. The harness works with an environment, but the environment does not own it.

Every environment must have a grader. Ungraded rows enter Monte only one way: frozen as a dataset and stated as an sft run's source, never as part of an environment or an experiment. One environment can serve several experiments: the same tasks, frozen under different settings.

Monte measures any environment from the NeMo Gym catalog, and a custom environment ships as an installable package.

## Why a Freeze Is Kept

Freezing the same tasks a second time reads live sources again, so the files come back different. Different files are a different fingerprint, which is a different experiment, and every baseline taken under the old one stops meaning anything.

Those bytes cannot be made a second time, so they have to outlive the machine that made them. A frozen environment is therefore kept off the box that uses it, and any copy on a machine is proven against its hash rather than trusted. Checkpoints live on Hugging Face for the same reason.

## How a Graded Rollout Runs

A rollout runs across three servers: one for the model, one for the agent harness, and one for the environment's grader.

1. The harness reads one task from the split. The split is a list of task IDs.
2. The harness sends the task to the model server, with the prompt already applied, and collects the reply.
3. The harness sends the reply to the grader.
4. The grader returns a reward and the answer that it extracted.
5. Monte records one trace for each task, then writes the score to the Ledger.

A training run uses the same grader, and although eval and training each run their own copy of it, preflight, the set of checks Monte runs before it launches anything, proves that the copies match. The reward that the model learns from and the score that the eval reports therefore come out of one implementation.
