---
title: "Experiments"
---

An experiment is a fixed standard for scoring a model. Two runs under the same experiment answered the same tasks under the same rules, so they can be compared directly.

An experiment is built on one [Environment](/concepts/environments), and it fixes which of that environment's tasks run, the sampling rules, and what constitutes correctness.

## Why an Experiment Exists

Evaluation has many variables to set. You can give each task one attempt or several, change the decoding temperature, run a different subset of the tasks, or mark answers more or less strictly. Each choice returns a different number for the same model, and none is wrong. They answer different questions about how well the model completes the task.

An experiment holds those variables constant, so within one experiment the model is the only variable that changed between two runs. Any number of experiments can be defined.

When the variables go unrecorded, old results become unreliable. Without knowing the configuration of a result, nothing explains why two numbers differ, so the experiments that produced them cannot be compared.

## What an Experiment Fixes

An experiment fixes three things at creation.

1. **Tasks:** Which tasks run, as an exact list. Not a count and not a name, but those specific tasks.
2. **Evaluation Settings:** How the model is sampled: the decoding, the temperature, and how many attempts each task gets.
3. **Grader:** Which grader scores the answers, and the prompt the model saw.

An experiment fixes the evaluation only, not the training. The [Recipe](/concepts/training#recipes) stays free, and so does the source, what a run trains on, because those are what agents change between runs.

An Experiment names no model either: each Run binds its own, so many models can be compared under one Experiment.

Monte checks the frozen material before every run. If any of it changed, that is a different experiment, and Monte refuses to score the new run against the old ones.

## The Splits

An experiment owns its splits, and the trainer and the evaluator both read the same lists, which is what holds the roles below in place. An experiment over a trainable environment carries all three. One over an eval-only environment carries dev alone when that environment was frozen from a single benchmark, and dev and test when it was frozen from two, which is the form that can carry a final claim.

- **Train:** What the model learns on.
- **Dev:** What agents read to choose the next move.
- **Test:** Held back for the baseline and the final claim.

Agents pick each next move from what dev shows, so the loop fits itself to those tasks over time. A dev score therefore overstates the model, which is why dev is not the number to report. test stays out of the loop entirely, and it gets two reads: the first is taken deliberately, as an eval of the base model before any training begins, and the second is the final claim, after which Monte refuses a third. Skip that first read and Monte refuses the claim as well, because there would be nothing to compare it against. [Improvement](/concepts/improvement) covers how those reads happen.
