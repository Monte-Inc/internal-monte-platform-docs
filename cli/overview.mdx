The `monte` CLI is the only write path into the platform. This page states the conventions once, then lists every command.

## Conventions

- **Default subverb.** `monte eval math` means `monte eval run math`. Same for `train`. Options may precede the name: `monte eval --smoke math` works. The `env` and `box` groups have no default on purpose: their subcommands are different intents.
- **Confirm before launch.** `eval run` and `train run` print the Run plan, then ask `launch?`. Skip the prompt with `--yes`. Without a TTY the prompt refuses (`E_CONFIRM`) instead of hanging. `--dry-run` prints the plan and launches nothing. The plan you approve is the exact object persisted as `plan.json` and hashed into the row's provenance.
- **Typed confirm for promote.** `promote` does not ask y/n. You must pass `--confirm <measurement-name>`, typed out. A mismatch is the same `E_CONFIRM`.
- **`--json`.** Supported on `eval run`, `train run`, `status`, `show`, `env add`, `env list`, `config`, `sync`, `push`, and every `box` subcommand. Stdout carries pure JSON: the human plan summary moves to stderr. One trap: `status --json` omits the checkpoint ladder that the human view prints.
- **Refusals.** Anything the platform declines exits 3 or higher with `CODE: cause (fix)` on stderr. The fix is part of the message.
- **`--version`.** `monte --version` prints the installed version and exits.

## Where a command runs

Three groups, and mixing them up is the most common source of a refusal.

| Group | Runs from | Commands |
| --- | --- | --- |
| Anywhere | a tool install or a checkout | `init`, `status`, `logs`, `show`, `env`, `config`, `sync` |
| Laptop, checkout only | a clean git checkout pushed to origin | `--remote` on `eval` and `train`, `box` |
| Box-side | the GPU box holding the Checkpoint | real `eval` and `train`, `--push`, `promote` |

`--remote` reads the git state of the checkout it runs from, so a `uv tool` install refuses it (`E_REMOTE`). `promote` copies weights off disk, so it runs where they live.

## Commands

### monte init

```bash
monte init <measurement> --env <environment> [--recipe <recipe>]
```

Creates the Measurement: freezes the Splits, the eval settings, and the Environment fingerprint into `measurement.json`. Refuses an existing name (`E_MEASUREMENT_EXISTS`).

`--recipe` freezes the training [Recipe](/concepts/training#recipes) into the Measurement. A trainable Environment requires it. An eval-only Environment refuses it, because a yardstick never trains and the Recipe would be recorded and never read. The name is checked at init, so a typo fails here rather than at the first `monte train`.

### monte eval

```bash
monte eval <measurement> [--model M] [--split dev|test] [--step N] [--smoke]
                         [--remote] [--push] [--yes] [--dry-run] [--json]
```

Scores a model on a Split and appends the row. The default Split is dev. The default step is the Cohort's newest Checkpoint. Test evals are budgeted: Baseline and final claim only.

`--remote` submits the Run to an ephemeral GPU box and returns. `--push` uploads results to the durable tier after each transition, and is what the box job itself runs with. See [Remote runs](#remote-runs).

### monte train

```bash
monte train <measurement> [--model M] [--smoke] [--chained]
                          [--remote] [--push] [--yes] [--dry-run] [--json]
```

Trains one chunk, chained from the Cohort's newest Checkpoint. Refuses without a Baseline (`E_NO_BASELINE`). `--smoke` runs a capped micro-chunk that is never evidence. `--chained` only matters with `--smoke`: real runs always chain.

The [Recipe](/concepts/training#recipes) comes from the Measurement, frozen at `monte init`. A Run cannot choose one: a training method picked per Run is not a Measurement, so there is no `--recipe` flag here. A Recipe may name its own model, and `--model` still wins. Both the name and the file's content hash land in the Run's plan, and the bytes in the run directory.

`--remote` and `--push` work as they do on `eval`, with one addition: a real chunk's Checkpoints go to Hugging Face at the end of a `--push` run, so a real `--remote` train needs a Hugging Face token. `--remote` also refuses a Measurement that froze its Recipe by path, because the box resolves the Recipe in its own checkout, where that file does not exist. Commit the file to `recipes/` and init a new Measurement that names it, or run without `--remote`.

Chaining is same-Recipe only: a chunk whose Recipe differs from the Checkpoint it would resume is refused, naming both, because the result would be half one method and half another. Starting a second method deliberately needs an explicit parent, which is not built yet.

### monte status

```bash
monte status <measurement> [--json]
```

Prints the Run rows and the per-Cohort delta lines, paired when possible and labelled unpaired when not. Also prints each Cohort's Lineages — the descent paths, one line each, labelled with the Recipe per hop — its Cycles with their strike verdicts, and the checkpoint ladder. `--json` carries the same paths, with the evals on every hop.

### monte logs, show, stop

```bash
monte logs <measurement>/<run> [--follow]
monte show <measurement>/<run> [--json]
monte stop <measurement>/<run>
```

`logs` prints the Run's event file as JSON lines. `show` prints one full row with all provenance fields. `stop` terminates a running Run and the row reads as abandoned.

### monte promote

```bash
monte promote <measurement>/<run> --dest <path|user@host:path> --confirm <measurement>
```

Exports a succeeded training Run's servable Checkpoint to `--dest`, sha256-verified. It then prints the file count and the destination disk usage.

### monte env

```bash
monte env add --benchmark <benchmark> [--as <name>] [--json]
monte env add --server <server> --dev <benchmark> --test <benchmark>
              [--as <name>] [--json]
monte env list [--available] [--json]
monte env install <name>
monte env install --all
```

`add` freezes what the Gym checkout ships into an Environment of your own. It runs Gym's prepare once, pins the bytes, and writes the manifest. That prepare is the only network step in an Environment's life: `install` and verify read the pinned bytes and never download again. Frozen means frozen, so re-adding a name refuses.

The two forms differ in what the Environment can do. `--benchmark` freezes one exam as an eval-only Environment: a yardstick that scores models and never trains. `--server` freezes a resources server's training curriculum together with the `--dev` and `--test` exams you name, which makes the Environment trainable. `--server` requires both exams at add time, because a frozen Environment cannot gain a test exam later and would otherwise never be promotable. `--as` names the result, and the default is the source name verbatim. Freezing needs a Hugging Face token. A wrong combination of these flags is a usage error and exits 2.

`list` shows each Environment and its Gym benchmarks. `--available` browses what the Gym checkout ships instead, with nothing frozen. `install` verifies frozen data against its manifest and registers the benchmark configs. Install is idempotent. A mock-only Environment prints a note instead.

### monte sync, push

```bash
monte sync [measurement...] [--bucket B] [--key-file PATH] [--json]
monte push <measurement> [--run R] [--bucket B] [--key-file PATH] [--json]
```

The two directions of the durable tier, a results bucket that outlives any box.

`sync` pulls the bucket into a local Mirror, defaulting to every Measurement in it. The Mirror is a read-only view: the durable copy wins on disagreement, local-only files are never deleted, and weight objects are skipped because weights live on Hugging Face.

`push` uploads one Measurement's local results tree, new and changed files only. `--run` narrows it to a single Run plus the Measurement's own files. Nothing remote is ever deleted, so retention stays a separate deliberate act. Weight files are refused passage.

Both resolve a GCS service-account key: `--key-file`, then `MONTE_GCS_KEY_FILE`, then the 1Password document `MONTE_GCS_KEY_OP` names, fetched in memory. Without one, `E_STORAGE`.

### monte box

```bash
monte box up [--type T] [--region R] [--cold] [--ssh-key K] [--json]
monte box status [--json]
monte box down <instance-id|name> [--json]
```

Ephemeral Lambda GPU boxes, managed from your laptop.

`up` shops for capacity in the NFS's home region first, then anywhere. It waits until the instance is active, writes the identity file, and arms a watchdog: a systemd timer that terminates the box through the Lambda API once it goes idle past its budget or over its hard TTL. Every box is born able to kill itself. `--cold` launches without the NFS data root, which means the box cannot serve a real Run.

`status` lists every instance on the account. Monte's own boxes show age and an over-TTL flag. Anything else is listed read-only as foreign.

`down` terminates one box through the API, never an OS shutdown, because Lambda keeps billing a halted instance. Foreign instances are refused.

All three resolve a Lambda API key from `MONTE_LAMBDA_KEY` or the 1Password item `MONTE_LAMBDA_KEY_OP` names. Without one, `E_BOX`.

### monte config

```bash
monte config [--json]
```

Prints the resolved configuration: the data root and its source, the GPU check command, mock seconds, the base-model pin, the installed Environments, the resolvable Recipe names with their search path, and the schema version.

## Remote runs

`monte eval --remote` and `monte train --remote` move one Run onto an ephemeral box and return. The flow is fixed:

1. **The reproducibility gate.** Your working tree must be clean and `HEAD` must be contained in origin. The box checks out exactly that commit, so an uncommitted or unpushed change would make the recorded `git_sha` a lie. This is a refusal, never a warning, and it is why `--remote` needs a checkout rather than a tool install.
2. **A box.** An active box is reused when it fits. If none fits, Monte launches and arms one. A real Run needs a warm box, because that is where the data root lives.
3. **The code.** Shipped as a git bundle at the recorded commit, then `uv sync` on the box.
4. **The credentials.** Planted under `/etc/monte/secrets`, streamed over stdin rather than passed as arguments.
5. **The tree.** Seeded by the box's own `monte sync`, so there is one transfer path and never a second.
6. **The job.** Launched detached in a tmux session. It pushes results at each transition and the box terminates itself when the job ends.

The Measurement must already exist locally, so a typo refuses on your laptop instead of dying in a detached session an hour of billing later. `--remote` refuses alongside `--push` (the box job already runs with it) and alongside `--dry-run` (submitting launches real compute, which is the opposite of dry).

Watch a submitted Run with `monte sync <measurement>` and then `monte status <measurement>`, which is never more than one transition behind live.

## Environment variables

Paths and execution:

| Variable | Meaning | Default |
|---|---|---|
| `MONTE_ROOT` | durable data root: Measurements, Ledger, Splits | `~/monte-post-training/monte-platform` |
| `MONTE_LOCAL` | disposable box-local root: venvs, caches, scratch | `~/monte` |
| `MONTE_RECIPES` | a directory of Recipes, searched before the packaged ones | unset |
| `MONTE_GPU_CHECK_CMD` | command for the foreign-process GPU check in a real preflight. Empty disables that check | auto |
| `MONTE_MOCK_SECONDS` | duration of a mock run, in seconds | `30` |
| `MONTE_GPU_MEM_UTIL` | fraction of GPU memory the eval server can claim | `0.9` |
| `MONTE_DOCKER` | docker command override, for example `sudo docker` | `docker` |

Credentials. Each one resolves from a direct value first, then from 1Password, which is fetched in memory so nothing lands on disk:

| Variable | Meaning | Default |
|---|---|---|
| `MONTE_LAMBDA_KEY` | Lambda API key for `box` and `--remote` | unset |
| `MONTE_LAMBDA_KEY_OP` | 1Password item holding it instead | unset |
| `MONTE_GCS_KEY_FILE` | GCS service-account JSON path for `sync` and `push` | unset |
| `MONTE_GCS_KEY_OP` | 1Password document holding it instead | unset |
| `MONTE_GCS_BOX_KEY_FILE` | the key planted on a box, when it differs from yours | unset |
| `MONTE_GCS_BOX_KEY_OP` | 1Password document holding that one | unset |
| `HF_TOKEN` | Hugging Face token: a real train pushes Checkpoints there | unset |
| `MONTE_HF_TOKEN_OP` | 1Password item holding it instead | unset |
| `MONTE_HF_ORG` | Hugging Face org the weights repos live under | `monte-inc` |
| `MONTE_OP_ACCOUNT` | 1Password account for every `op` lookup above | unset |
| `MONTE_OP_VAULT` | 1Password vault for every `op` lookup above | unset |

Box provisioning:

| Variable | Meaning | Default |
|---|---|---|
| `MONTE_SSH_KEY_NAME` | account SSH key name, needed when the account has several | unset |
| `MONTE_NFS_NAME` | the NFS a warm box attaches | `monte-post-training` |

## Exit codes

| Code | Name | Fires when |
|---|---|---|
| 0 | success | |
| 1 | aborted | Ctrl+C at the confirm prompt, or a broken pipe |
| 2 | usage | Click usage errors: a bad flag or a missing argument |
| 3 | `E_NO_BASELINE` | train without a matching-Cohort Baseline |
| 4 | `E_FROZEN_FIELD` | a launch would change a frozen Measurement field |
| 5 | `E_NOT_COMPARABLE` | comparability config does not match the Cohort |
| 6 | `E_PREFLIGHT` | preflight failed: fingerprint drift, disk floor, test budget |
| 7 | `E_CONFIRM` | declined prompt, non-TTY without `--yes`, or a promote `--confirm` mismatch |
| 8 | `E_MEASUREMENT_EXISTS` | init on a name that exists |
| 9 | `E_NOT_FOUND` | no such Measurement, Run, or promotable Checkpoint |
| 10 | `E_NOT_RUNNING` | stop on a Run that is not running. Exception: an abandoned Run with an orphaned container is still stoppable |
| 11 | `E_CORRUPT_STATE` | Ledger or pairing state is inconsistent |
| 12 | `E_SERVING` | the eval serving stack failed |
| 13 | `E_VERIFICATION` | a promote checksum or load verification failed |
| 14 | `E_STORAGE` | the durable tier is unreachable: credentials, package, or path |
| 15 | `E_BOX` | a box could not be provided or operated on: credentials, capacity, the Lambda API refusing, or a foreign instance |
| 16 | `E_REMOTE` | a remote submission could not be made: a dirty or unpushed tree, a box that cannot serve the Run, or a shipping step failing over SSH |
