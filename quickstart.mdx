---
title: "Quickstart"
---

<Note>
  Monte is in closed beta. Interfaces and these docs change quickly, and commands can break between versions.
</Note>

This walkthrough runs the Monte loop end to end on a laptop: install the CLI, initialize an experiment, score a baseline, train a checkpoint, and score it against that baseline. That is the whole post-training pipeline, start to finish, and it runs the same way before it is pointed at real work.

Monte is in closed beta, so read access to `Monte-Inc/internal-monte-platform` is required. Everything below runs through [uv](https://docs.astral.sh/uv): it fetches its own Python, and the repo is never cloned.

<Steps>
  <Step title="Install the CLI">
    ```bash
    uv tool install git+ssh://git@github.com/Monte-Inc/internal-monte-platform \
      --with "git+ssh://git@github.com/Monte-Inc/internal-monte-platform#subdirectory=environments/demo"
    ```
    This places `monte` on the PATH, so every command below is invoked as bare `monte`.

    The `--with` line adds the `demo` environment. Environments ship alongside the CLI but install separately: each is its own package, and installing one is what registers it. Keep the quotes around that URL.
  </Step>
  <Step title="List the Installed Environments">
    ```bash
    monte env list
    ```
    This walkthrough installs one environment, so the command lists `demo`. It is trainable and mock: its curriculum supplies the training tasks, and it runs without a GPU box.
  </Step>
  <Step title="Initialize an Experiment">
    ```bash
    monte experiment init hello --eval demo
    ```
    This freezes the splits, the eval settings, and the environment fingerprint. `--eval` names the environment whose exams decide what "better" means. Every score in this experiment comes from there. The name `hello` is arbitrary.

    Nothing about training is frozen here. The method and the data are stated on each run, in the steps that follow.
  </Step>
  <Step title="Run the Baseline Eval">
    ```bash
    monte eval hello
    ```
    The CLI prints the run plan and asks `launch?`. The mock run takes about 30 seconds. This baseline eval scores the dev split and lands as `eval@0`, the score every later run is compared against.
  </Step>
  <Step title="Score the Base Model on Test">
    ```bash
    monte eval hello --split test
    ```
    Run this now, before any training. `monte eval` scores the dev split unless told otherwise, so the baseline eval above did not touch test.

    The test split is read exactly twice per cohort, and a cohort is the set of runs that share one base model, one frozen environment, and one set of eval settings. Every run in this walkthrough is in the same cohort. The first read is this one, on the base model. The second is the final claim after training, which is the test score of the checkpoint Monte selects. Having both reads is what allows the improvement to be stated on tasks the loop never saw.

    Do not skip this step. After training begins, Monte refuses the later test eval: no baseline exists to pair against, so the cohort can never state a test delta.
  </Step>
  <Step title="Rehearse with a Smoke Run">
    ```bash
    monte train hello --recipe grpo_math_1B --source demo --smoke
    ```
    A run is the fixed unit `monte train` trains: 50 steps by default, and 3 steps for a smoke. A step count is never stated.

    Three things accompany every training run, and Monte infers none of them. `--recipe` is the method: `grpo_math_1B` ships with the CLI, and `monte config` lists the rest. `--source` is what the run trains on, here the `demo` curriculum. The third is the starting point, and `--smoke` is the one case that states none: a smoke rehearses the from-scratch path.

    A smoke run is a capped sanity pass. It is never evidence: it cannot be a baseline, a parent, or a promote source.
  </Step>
  <Step title="Train a Real Run">
    ```bash
    monte train hello --recipe grpo_math_1B --source demo --from-base
    ```
    Now the starting point is stated. `--from-base` opens a fresh branch from the base model at step 0. The other way to start is `--parent <run>/<step>`, which continues an existing checkpoint. `monte status` prints the exact spelling.

    This run is 50 steps and it does count as evidence.
  </Step>
  <Step title="Score the New Checkpoint">
    ```bash
    monte eval hello
    ```
    With no target flag, an eval scores the cohort's newest checkpoint. That is the run just trained, so this row lands as `eval@50`.
  </Step>
  <Step title="Read the Ledger">
    ```bash
    monte status hello
    ```
    After the five runs above, the whole ledger prints:

    ```text
    RUN                         KIND      STATUS     SCORE                    PID     STARTED
    01M0GG8W3EN5W9FRSHE8ECFGE4  eval@0    succeeded  dev=0.6667±0.3772        -       2026-08-20T21:12:14+00:00
    01M0GG9T3THPVPZ6DD2JQZ53NZ  eval@0    succeeded  test=0.3333±0.3772       -       2026-08-20T21:12:44+00:00
    01M0GGAWK6A7DF1QH75QS8TCGP  train@3   succeeded  -                        -       2026-08-20T21:13:20+00:00  [not evidence]
    01M0GGBTKSWZHRTCPJRR25J6S3  train@50  succeeded  -                        -       2026-08-20T21:13:50+00:00
    01M0GGCRHY8FHNRWS310YE0ZCS  eval@50   succeeded  dev=1.0±0.0              -       2026-08-20T21:14:21+00:00

    cohort Qwen/Qwen2.5-1.5B-Instruct@mock-m1: dev 0.6667 -> 1.0 (delta +0.3333 ± 0.3772 paired, 2 fixed / 0 broken, eval@50)
      lineage: base -grpo:demo-> 50
      cycles: eval@50 +0.3333 ±0.3772 STRIKE  (1 strike)
      presents 01M0GGBTKSWZHRTCPJRR25J6S3/step_50 of cohort Qwen/Qwen2.5-1.5B-Instruct@mock-m1 (dev 1.0000, +0.3333 vs the Baseline)
        chosen by the claim rule (highest paired dev delta, which is not always the deepest step)

    checkpoints:
      step 50    written by 01M0GGBTKSWZHRTCPJRR25J6S3  (load-check ok, servable)
    ```

    Three sections, top to bottom: the Run Ledger, the Cohort Block, and the Checkpoint Ladder.

    **Run Ledger**

    One row per run, in the order they started. `KIND` is the kind and the step it sits at, which is why both baseline evals read `eval@0`: they scored the same untrained model, one on dev and one on test. The smoke is `train@3` and carries `[not evidence]`, the marker for a row nothing may be built on.

    **Cohort Block**

    One block per cohort, and this walkthrough produced one.

    `cohort Qwen/Qwen2.5-1.5B-Instruct@mock-m1` is the base model and its pinned revision. `dev 0.6667 -> 1.0` is the dev score at the baseline and at `eval@50`, the newest eval.

    `delta +0.3333` is the gap between those two scores. `paired` means both evals scored the same frozen tasks, so Monte compared them task by task: `2 fixed / 0 broken` counts the flips, and tasks that landed the same way twice cancel. `± 0.3772` is the interval around the delta, and pairing changes that interval rather than the delta itself.

    `lineage:` is the path from the base model to this checkpoint, one arrow per training run, labelled with the move it made. Here `grpo` on the `demo` source took the base model to step 50.

    `cycles:` is the verdict at each new highest step along that path. `STRIKE` means the paired dev delta is not significantly positive: 0.3333 minus 0.3772 falls below zero, so the gain could be noise. `(1 strike)` is the cohort's running total.

    `presents` names the checkpoint Monte would claim as the result, and the line beneath it says why that one won.

    **Checkpoint Ladder**

    Every step an evidence train run saved, each naming the run that wrote it and what was verified about it. `load-check ok` means the weights were loaded back and read cleanly; `servable` means a servable copy exists. The smoke wrote nothing here, which is what `[not evidence]` buys.
  </Step>
</Steps>

<Note>
A real score needs a GPU box, and running on one needs a checkout of the platform repo rather than this tool install. Those instructions are being rewritten and are not on this site yet.
</Note>
