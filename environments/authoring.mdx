<Note>
Most Environments are not authored. If the exam or the curriculum you want already ships with NeMo Gym, freeze it instead: `monte env add` runs Gym's prepare once, records a hash of the files, and writes the manifest for you. See [monte env](/cli/overview#monte-env). Author a package when the graded world is yours and Gym has nothing to freeze.
</Note>

An Environment is its own Python package under `environments/`, a uv workspace member with its own `pyproject.toml`. `demo` is the minimal shape and the only example that ships today.

## Package shape

Register the loader as an entry point:

```toml
[project.entry-points."monte.environments"]
demo = "monte_env_demo:load_environment"
```

Installing the package is what registers the Environment. The entry point is the only way Monte finds one.

Implement the protocol: `splits()`, `grade()`, `fingerprint()`, and the optional `install()` and `verify_install()`. `demo` implements the first three in about 60 lines, and that is enough to run the whole loop in mock.

An Environment is trainable when `splits()` returns a `train` key, and eval-only when it does not. Only a trainable Environment can be a `--source` for `monte train`.

## Rules that bite

- **Never depend on `monte`.** Declaring `monte` in your `pyproject.toml` creates a circular dependency in the uv workspace. And the resources server runs in its own venv with no `monte` installed, so a top-level `import monte` crashes it. Import `monte` lazily inside functions, never at module top.
- **The prompt template is yours, and it is frozen.** The Environment owns its prompt file, and the prompt bytes are part of the fingerprint. An edit to the prompt is a Measurement change, not a tweak.
- **One name, once.** A duplicate Environment name across installed packages refuses as soon as Monte looks for Environments. A broken `load_environment()` raises a Refusal that names the installed package.

## Going beyond mock

`demo` is mock-only: it declares no Gym benchmarks, so it has no real-execution half. A package that scores real models needs three more things, and no shipped package demonstrates them. The `math` worked example was deleted rather than kept half-current.

- **Frozen data.** Real task data never lives in the repo. You copy it onto the data root from a copy whose bytes already match the manifest, and you never derive it on a box. Your `install()` checks the files against `manifest.json` and registers the Gym benchmark configs. Install must be idempotent. `monte env add` pushes what it freezes to [the vault](/concepts/environments#where-an-environment-lives), which is what makes a data root copy replaceable. A package you author is not pushed there, so hold your own durable copy of those bytes.
- **The Gym rows file.** Each `*.gym.jsonl` file, re-derived from the frozen source through the current prompt renderer. These are the rows Gym reads.
- **The resources server.** Your FastAPI grading app plus its configs, copied to a name-derived Gym path. Training and eval both grade through this one server.

If this is where you are heading, read what `monte env add --server` produces first. It freezes exactly this shape, and matching it is easier than inventing it.

## Test what you wrote

1. `uv run pytest`: the `test_env_*` files cover grader and install-hook behavior.
2. `gym env test --resources-server <name>` exercises the resources server. `gym env start` plus a POST to `/verify` checks it while it is running. These are Gym commands, not monte ones.
3. `monte env list` confirms Monte found your package, and prints the kind it derived. `monte env install <name>` on the box verifies the data.
4. `monte experiment init <name> --eval <environment>`, then `monte eval <name> --smoke`: this puts your grader through the real CLI and writes a real Ledger row. The `--smoke` row stays in the Ledger but never counts as evidence.
